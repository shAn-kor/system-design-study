23:## 참고자료 기반 설계 관점 정리
32:기본 링만으로는 두 번째 목표가 잘 깨진다. 서버를 링 위에 한 점씩만 놓으면 랜덤하게 생긴 구간 크기 차이 때문에 특정 서버가 큰 구간을 맡을 수 있다. 그래서 Tom White의 설명처럼 실제 구현에서는 한 물리 서버를 여러 위치에 배치하는 가상 노드를 둔다. 가상 노드 수가 늘어날수록 한 서버가 여러 작은 구간을 나누어 맡게 되어 전체 부하가 평균에 가까워진다. 단, 가상 노드가 많아지면 링 메타데이터와 lookup 비용도 커지므로 "균등 분산"과 "관리 비용" 사이에서 개수를 정해야 한다.
34:분산 저장소에서는 링이 단순한 캐시 배정표가 아니라 파티션과 복제의 기준이 된다. Dynamo는 키 공간을 안정 해시로 나누고, 각 물리 노드에 여러 토큰을 부여해 부하를 분산한다. 키의 담당 노드뿐 아니라 링에서 이어지는 N개의 물리 노드를 preference list로 보고 복제 후보를 만든다. 이때 가상 노드 때문에 같은 물리 노드가 여러 번 나올 수 있으므로, 실제 preference list는 서로 다른 물리 노드가 들어가도록 건너뛰며 만든다. Cassandra도 링에서 키의 coordinator를 정하고, 그 coordinator와 후속 노드들을 복제 대상으로 삼는다. 다만 기본 랜덤 배치가 불균등하거나 노드 성능 차이를 반영하지 못한다는 한계가 있어서, Cassandra 논문은 여러 위치 배치 또는 부하 정보를 보고 노드를 이동시키는 방식을 언급한다.
36:운영 시스템에서는 "키가 어디에 저장되는가"만큼 "lookup이 얼마나 빠른가"도 설계 포인트가 된다. Discord 사례는 안정 해시 링 조회가 세션 재연결의 hot path가 되면, 링 자체는 맞게 설계되어 있어도 링을 조회하는 프로세스가 병목이 될 수 있음을 보여준다. 그래서 링 데이터를 여러 프로세스가 빠르게 읽을 수 있는 구조로 옮기고, 복사 비용을 줄이는 방식으로 lookup 비용을 낮췄다. 즉 안정 해시 설계는 링 배치 알고리즘에서 끝나는 게 아니라, 런타임에서 링 조회 경로가 병목이 되지 않도록 캐싱/공유 구조까지 포함해야 한다.
38:로드밸런서에서는 안정 해시의 우선순위가 조금 달라진다. Maglev는 connection tracking과 함께 일관된 backend 선택을 제공한다. 여기서 중요한 것은 backend 변경 시 기존 연결이 최대한 같은 backend로 가는 minimal disruption과, 모든 backend가 거의 같은 수의 연결을 받는 load balancing이다. Maglev는 큰 lookup table을 만들어 빠르게 backend를 찾고, 전통적 consistent hashing보다 균등 분산을 더 강하게 맞추는 쪽으로 설계했다. 대신 완전한 minimal disruption만을 최우선으로 두지는 않고, connection tracking과 함께 현실적인 균형을 잡는다.

50:## 참고자료별 설계 포인트
53:- Tom White, Consistent Hashing: 키와 캐시 서버를 같은 해시 함수로 링에 올리고, 가상 노드로 분산 균형을 보완하는 설명이 가장 직관적이다.
54:- Dynamo 논문: 안정 해시를 파티셔닝과 복제 preference list의 기반으로 사용하며, 여러 토큰/가상 노드를 통해 균등 분산을 개선한다.
55:- Cassandra 논문: 링에서 coordinator를 정하고 복제 정책을 붙이는 방식, 그리고 기본 안정 해시가 불균등 분산과 이기종 노드 문제를 가진다는 점을 보여준다.
56:- Discord Elixir 확장 사례: 안정 해시 링 조회가 hot path가 되었을 때 자료구조 공유와 lookup 비용 최적화가 별도 설계 문제가 된다는 사례다.
58:- Maglev 논문: 로드밸런서에서는 minimal disruption과 load balancing을 함께 만족해야 하며, lookup table 기반 설계가 실전 성능 요구와 연결된다.
