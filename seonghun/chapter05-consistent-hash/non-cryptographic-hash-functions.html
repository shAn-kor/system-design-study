그림으로 뜯어보기

사용자가 원한 핵심은 “표”가 아니라 각 함수가 무슨 방식으로 데이터를 섞고, 어디에 강하고, 어디에 약한지다. 그래서 아래는 알고리즘별로 동작 직관, 그림, 실무 판단 기준을 따로 정리했다.

해시테이블파일 중복 탐지체크섬샤딩·파티셔닝보안용 아님

먼저 큰 그림: “빠르게 섞기”와 “오류 검출”은 다르다

해시테이블·중복 탐지형

xxHash, MurmurHash3, CityHash, FarmHash, FNV-1a, Jenkins는 입력을 빠르게 섞어서 균등한 숫자로 보내는 것이 목적이다.

오류 검출형

CRC32/CRC64, Adler-32는 “균등 분포”보다 전송·저장 중 비트가 깨졌는지를 잡는 쪽에 가깝다.

MurmurHash3와 XXH3, 같은 일을 하는 두 믹서

둘 다 긴 문자열이나 숫자 키를 고정된 숫자로 바꿔 준다. 그 숫자를 해시 링 위의 위치로 쓰면, 키를 여러 서버에 나눠 담을 수 있다. 차이는 숫자를 섞는 방법, 속도를 노리는 방향, 기존 시스템과의 호환성이다.

초등학생식 비유

친구 이름을 받아서 사물함 번호로 바꾸는 기계가 있다고 하자. MurmurHash3와 XXH3는 둘 다 이름을 번호로 바꾸지만, 안에서 번호를 섞는 레시피가 다르다. 그래서 같은 이름도 두 기계에서는 다른 번호가 나올 수 있다.

이름 뜯어보기 MurmurHash3

곱하고 돌리는 해시의 3번째 설계

Murmur는 내부에서 자주 쓰는 두 동작을 줄여 부른 이름이다. MU는 Multiply, 숫자를 곱하는 동작이고 R은 Rotate, 비트를 빙글 돌리는 동작이다.

뒤의 Hash는 입력을 숫자로 바꾼다는 뜻이고, 3은 MurmurHash 계열의 세 번째 설계 세대라는 뜻이다.

MU + R + Hash + 3
“곱하고 돌려서 섞는 Murmur 계열의 3번째 해시”
이름 뜯어보기 XXH3

아주 빠른 xxHash 계열의 새 설계

xxHash는 공식 저장소에서 Extremely fast Hash algorithm, 즉 “매우 빠른 해시 알고리즘”이라고 설명한다.

XXH는 함수 이름에 붙는 계열 표시이고, 3은 XXH32·XXH64와 구분되는 XXH3 설계를 가리킨다. 다만 xx 각각을 어떤 단어의 약자로 정했다는 공식 설명은 없다.

xxHash + 3
“빠른 xxHash 계열에서 나온 XXH3 설계”

한 줄 요약 오래 검증된 범용 믹서. 여러 언어와 시스템에서 찾기 쉽다. 현대 CPU를 겨냥한 고속 믹서. 큰 입력과 많은 키를 빠르게 처리하는 데 초점을 둔다.
어린이 비유 종이를 작은 칸으로 나눠 곱하고, 돌리고, xor한 뒤 마지막에 한 번 더 골고루 흔드는 번호표 기계 큰 종이를 여러 줄(lane)로 나눠 동시에 섞고, 마지막에 하나의 번호로 합치는 빠른 믹서
섞는 방식 블록을 곱하기 → 회전 → xor로 섞고, 마지막 avalanche 단계에서 작은 차이도 넓게 퍼뜨린다. 입력 길이에 맞는 경로를 고르고, 여러 lane과 accumulator를 활용해 섞은 뒤 64bit 또는 128bit 결과를 만든다.
속도 감각 높음. 범용성과 구현체 생태계를 함께 챙기는 선택이다. 매우 높음을 목표로 함. 특히 현대 CPU에서 많은 데이터를 처리할 때 강점이 드러난다.
출력 크기 변형에 따라 32bit 또는 128bit를 쓴다. 보통 64bit 또는 128bit를 선택한다. 출력 공간이 넓을수록 충돌 가능성을 낮추는 데 유리하다.
충돌과 보안 서로 다른 키가 같은 숫자가 되는 충돌은 가능하다. 보안용 해시가 아니므로 공격자가 일부러 충돌을 만들 수 있는 상황에는 쓰지 않는다. 마찬가지로 충돌은 가능하고 보안용 해시가 아니다. 비밀번호 저장에는 Argon2id·scrypt·bcrypt·PBKDF2처럼 전용 password hashing/KDF 계열을 검토한다.
안정 해시에서 서버 이름이나 가상 노드 이름을 숫자로 바꿔 링 위의 위치를 정한다. 같은 역할을 하되, 키가 아주 많거나 재배치 계산이 잦을 때 속도 우선 믹서로 고려한다.
강점 자료와 구현체가 많고, 다른 언어·기존 시스템과 맞추기 쉽다. 빠른 처리량, 64/128bit 선택지, 짧은 입력과 긴 입력을 모두 고려한 설계가 강점이다.
주의할 점 버전과 변형(MurmurHash3_x86_32, x64_128 등)을 정확히 고정해야 다른 프로그램과 결과가 달라지지 않는다. XXH3와 기존 xxHash 변형을 구분하고, 사용하는 라이브러리의 시드·출력 폭·바이트 처리 규칙을 고정해야 한다.
고르는 법 기존 시스템과 결과를 맞춰야 하거나, 여러 플랫폼에서 쉽게 구현해야 하면 먼저 검토한다. 새 시스템에서 처리 속도가 가장 중요하고, 팀이 XXH3 구현을 안정적으로 고정할 수 있으면 검토한다.

둘의 공통 흐름

  1. 키를 바이트로 읽는다.
  2. 곱하기, 회전, xor 같은 규칙으로 잘 섞는다.
  3. 고정된 숫자 하나를 만든다.
  4. 그 숫자를 해시 링에서 찾고, 시계 방향의 서버를 고른다.

결론만 기억하면

속도 우선이면 XXH3, 기존 결과·자료·구현체와의 호환성이 중요하면 MurmurHash3를 먼저 살펴본다. 둘 다 비암호학적 해시이므로 보안 목적에는 쓰지 않는다.

동작 직관

입력을 덩어리로 읽고, 여러 누산기(accumulator)에 곱셈·회전·xor를 반복해서 비트 변화를 빠르게 퍼뜨린다. XXH3는 최신 CPU에서 매우 높은 처리량을 노린 설계다.

아이 눈높이 비유

학교 사물함 줄에서 이름표를 보고 “몇 번째 자리로 보낼까?”를 빠르게 정하는 도우미와 비슷하다. XXH3는 key를 암호로 숨기거나 절대 겹치지 않게 만드는 것이 아니라, key를 하나의 숫자로 바꾼다.

동작 순서

  1. 입력 key를 정해진 인코딩의 byte로 읽는다.
  2. byte와 bit를 빠르게 섞어 작은 차이도 퍼뜨린다.
  3. 64bit 또는 128bit 같은 고정 크기 숫자를 만든다.
  4. 안정 해시에서는 그 숫자를 ring 위의 위치로 쓴다.
  5. ring에서 시계 방향으로 가다가 처음 만나는 서버를 고른다.

안정 해시에서의 역할

XXH3는 ring 안쪽의 “섞는 기계”다. 안정 해시는 숫자를 ring에 놓고 시계 방향 서버를 고르는 배치 규칙이며, virtual node가 있으면 서버 이름과 복제 번호도 같은 방식으로 섞어 여러 위치에 놓는다.

언제 선택할까?

큰 key, 파일 조각, 로그처럼 많이 그리고 빨리 처리해야 하면 XXH3가 속도 우선 선택지다. 대신 비암호학적 해시라 충돌은 가능하고, 저장·통신 계약에는 seed, 인코딩, 출력 크기, 버전을 적어야 한다.

장점

  • 대용량 데이터에서 처리량이 매우 좋다.
  • 64bit/128bit 출력을 고르기 쉬워 충돌 위험 조절이 쉽다.
  • 파일 fingerprint, 블록 dedup, 캐시 키에 적합하다.

약점

  • 암호학적 충돌 저항을 제공하지 않는다.
  • 데이터 포맷에 영구 저장하면 버전/구현 호환성을 명시해야 한다.

MurmurHash3

범용해시테이블 친화
Bloom filter샤딩분산 시스템

동작 직관

작은 블록을 상수와 곱하고 회전시키며 상태값에 섞는다. 마지막 avalanche 단계에서 입력의 작은 변화가 출력 전체에 퍼지게 만든다.

아이 눈높이 비유

도서관 책장 앞에서 책 제목을 보고 “어느 번호표를 붙일까?”를 정하는 규칙과 비슷하다. MurmurHash3는 key를 안전하게 숨기는 암호가 아니고, 같은 방식으로 읽은 key를 정해진 크기의 숫자로 바꾼다.

동작 순서

  1. 입력 key를 정해진 인코딩의 byte로 읽는다.
  2. byte와 bit를 곱셈, 회전, xor로 차례대로 섞는다.
  3. 32bit 또는 128bit 같은 고정 크기 숫자를 만든다.
  4. 안정 해시에서는 그 숫자를 ring 위의 위치로 쓴다.
  5. ring에서 시계 방향으로 가다가 처음 만나는 서버를 고른다.

안정 해시에서의 역할

MurmurHash3는 key와 virtual node 이름을 숫자로 바꾸는 mixer다. consistent hashing은 그 숫자를 어디에 놓고 어떤 서버를 고를지 정하는 placement rule이다.

언제 선택할까?

여러 언어의 구현체, 오래된 시스템, 일반적인 해시테이블·Bloom filter와 맞추기 쉬운 선택지가 필요하면 MurmurHash3가 익숙한 범용 선택지다. XXH3보다 최고 속도는 낮을 수 있고, 비암호학적 해시라 충돌은 가능하므로 seed, endian, 인코딩, 버전을 문서에 고정해야 한다.

장점

  • 많은 언어와 시스템에서 구현체가 있다.
  • 해시테이블, Bloom filter, consistent hashing 주변에서 익숙하다.
  • 32bit와 128bit 변형이 널리 쓰인다.

약점

  • xxHash/XXH3보다 최신 CPU 처리량은 낮을 수 있다.
  • seed와 endian/구현 차이를 문서화하지 않으면 호환 문제가 생긴다.

Jenkins hash

동작 직관

비트 이동과 xor, 덧셈을 반복해 작은 변화가 출력 전체로 퍼지게 한다. “one-at-a-time”, “lookup3” 같은 변형이 오래된 코드에서 보인다.

장점

  • 역사적으로 많이 쓰여 레거시 코드 이해에 유용하다.
  • 복잡한 곱셈 없이도 괜찮은 avalanche를 만들려는 설계다.

약점

  • 현대 신규 선택지로는 우선순위가 낮다.
  • 변형이 많아 “Jenkins hash”라고만 쓰면 정확한 호환성을 알기 어렵다.

동작 직관

  • 공격자는 CRC가 맞는 변조 데이터를 만들 수 있다.
  • 해시테이블 분산용으로는 일반 해시보다 목적이 다르다.

새 프로젝트의 빠른 비보안 fingerprint XXH3 64/128 속도와 품질이 좋고 현대적이다. 보안 무결성 증명에는 쓰지 않는다.
해시테이블, Bloom filter, 샤딩 MurmurHash3, xxHash 분산 품질과 생태계가 좋다. seed와 구현 버전을 고정한다.
문자열 키가 많은 기존 Google 계열 시스템 CityHash, FarmHash 문자열 처리에 최적화된 계열이다. 플랫폼 간 결과 안정성을 확인한다.
네트워크/파일 포맷 오류 검출 CRC32, CRC64 오류 검출이라는 목적에 맞다. 악의적 변조 방지는 못 한다.
매우 간단한 의존성 없는 구현 FNV-1a, Adler-32 직접 구현이 쉽다. 대규모 중복 판정에는 부적합할 수 있다.
보안 무결성, 서명 SHA-256, BLAKE3, HMAC 비암호학적 해시의 영역이 아니다. xxHash, CRC, Adler는 쓰지 않는다.
패스워드 저장 Argon2id, scrypt, bcrypt, PBKDF2 비밀번호 추측을 느리게 만드는 전용 KDF를 쓴다. xxHash, CRC, Adler, SHA-256은 쓰지 않는다.

중복 탐지 팁: 해시값이 같다고 바로 동일 파일로 확정하지 말고, 파일 크기 → 빠른 해시 → 필요 시 원본 바이트 비교 순서로 검증하면 안전하다.
