좋은 지도도 읽는 길이 막히면 느려져요

주의 실제 사실

먼저 범위를 확인해요

이것은 2017년 당시의 이야기예요

이 페이지는 Discord가 2017년에 공개한 엔지니어링 글의 한 사례를 쉽게 풀어쓴 학습 자료입니다. 글 제목에는 500만 동시 사용자가 나오지만, 본문은 “거의 500만 명”이라는 규모를 설명합니다. 쉬운 비유만으로 끝내지 않고, 비유가 실제 process·mailbox·heap·queue에서 무엇을 뜻하는지도 함께 설명합니다.

현재 상태로 오해하지 않기 이 글은 현재 Discord 아키텍처를 설명하는 자료가 아닙니다. 아래 시간도 2017년 당시 ring lookup 경로를 비교한 계산값이지, 전체 재접속 완료 시간이나 오늘의 Discord 성능이 아닙니다.
비유 실제 사실

1. 길찾기 규칙

안정 해시 링은 둥근 노선도예요

일반적인 안정 해시에서는 guild 같은 대상을 나타내는 key와 Erlang node를 같은 둥근 링에 놓습니다. key에서 정해진 방향으로 걸어가 가장 먼저 만나는 node가 담당 위치가 됩니다.

왜 이름이 “안정” 해시일까요?

일반적인 나머지 연산 방식에서는 서버 수가 바뀌면 많은 key의 계산 결과가 한꺼번에 달라질 수 있습니다. 안정 해시 링에서는 node 하나가 추가되거나 빠져도 그 node와 이웃한 링 구간의 key만 주로 새 담당자를 찾습니다. 전체 key를 다시 배치하는 일을 줄이는 것이 “안정”의 핵심입니다.

변화 링에서 일어나는 일 영향받는 key
node 추가 새 node가 자신의 앞쪽 링 구간 일부를 맡음 그 작은 구간에 있던 key만 새 node로 이동
node 제거 빠진 node의 구간을 다음 node가 이어받음 빠진 node가 맡던 key만 주로 이동
일반 원리와 Discord 원문 범위 구분 위 최소 재배치 설명은 안정 해시의 일반 원리입니다. Discord 공식 글은 node 추가·삭제 실험보다, 이미 사용 중인 ring을 매우 자주 조회할 때 생긴 hot path 병목과 읽기 경로 개선에 초점을 둡니다.
  1. STEP 1 WebSocket으로 접속
  2. STEP 2 session process 생성
  3. STEP 3 guild 목록 확인
  4. STEP 4 remote Erlang node 조회
  5. STEP 5 guild process와 통신
node 찾기와 PID 찾기는 달라요 ring이 먼저 찾은 것은 entity의 remote Erlang node입니다. 그 뒤 실제 guild process의 PID를 찾는 일은 별도 단계입니다. 둘을 한 번의 lookup으로 합쳐 생각하지 않습니다.

실제 시스템에서는 누가 무엇을 맡았을까요?

구성 요소 맡은 일 서로 주고받는 것
session GenServer WebSocket으로 접속한 사용자 한 명의 세션을 담당 관심 있는 guild마다 담당 remote node를 조회
ring process consistent hash ring을 소유하고 조회 요청을 처리 guild 같은 entity의 key를 받아 Erlang node를 반환
guild registry 찾아간 guild node 안에서 실제 guild PID를 조회 node 위치가 아니라 실행 중인 process 식별자를 반환
guild GenServer guild의 상태와 메시지 처리를 담당 session process와 실제 이벤트를 주고받음

2. 한곳에 생긴 긴 줄

모두 한 안내 데스크에 물어봤어요

처음에는 session process들이 ring을 관리하는 하나의 process에 request/reply로 물었습니다. 좋은 지도가 있어도 질문을 받는 곳이 하나라면, 사람이 몰릴 때 긴 줄이 생깁니다.

여기서 볼 것은 숫자가 아니라 줄의 위치예요 사용자가 많아질수록 모든 질문이 하나의 ring process에 모입니다. 그래서 해시 계산 자체보다 “누가 ring을 읽는가”가 병목이 됩니다.
이 그림은 성능 숫자 비교가 아니에요 한 번의 해시 계산이 오래 걸린다는 뜻이 아니라, 요청이 한 곳에 직렬로 모이면 대기 줄이 생긴다는 구조를 보여줍니다.

왜 process 하나가 전체 속도를 제한했을까요?

원인 내부에서 벌어지는 일 결과
직렬 처리 ring을 제어하는 한 process가 자신의 mailbox에서 요청을 하나씩 꺼냄 CPU core가 많아도 이 경로는 한 담당자의 처리량에 묶임
request/reply 요청 전송, 상대 process 실행, 답 전송, 호출자 깨우기가 필요함 ring 계산 외에도 process 사이 왕복 비용이 생김
재접속 burst 최대 50만 session이 평균 5개 guild의 node를 거의 동시에 물음 많은 요청이 짧은 시간에 mailbox로 몰림
de-scheduling BEAM scheduler가 공정성을 위해 바쁜 ring process도 잠시 멈출 수 있음 해시 계산 외에 대기와 스케줄링 지연이 더해질 수 있음
실제 사실

3. 첫 번째 개선

ETS에서 직접 읽게 했지만 복사가 남았어요

Discord는 ring을 pure Elixir로 바꾸고 ETS라는 빠른 메모리 테이블에 넣었습니다. 여러 process가 한 담당자에게 묻지 않고 직접 읽을 수 있게 된 점은 좋아졌습니다.

ETS는 무엇인가요?

ETS(Erlang Term Storage)는 BEAM VM 안에 있는 공유 인메모리 표입니다. 여러 process가 이름으로 같은 표를 찾아 직접 읽을 수 있으므로, ring 담당 process에게 메시지를 보낼 필요가 없습니다.

ring을 갱신하는 쪽 새로운 hash ring 값을 준비
표에 저장
ETS 표 여러 process가 직접 lookup 가능
큰 값 복사
session process의 heap 꺼낸 큰 ring 값이 여기로 복사됨

그래서 ETS는 중앙 대기 줄은 없앴지만, 큰 ring을 읽을 때마다 caller process의 heap으로 값이 복사되는 문제까지 없애지는 못했습니다.

최종 개선

FastGlobal 공유 읽기

큰 값을 매번 복사하지 않고 공유된 값처럼 바로 읽었어요.

최적화: 큰 값을 복사 없이 공유해 읽음

ETS가 나쁜 도구라는 뜻은 아니에요 이 사례에서는 큰 ring, 아주 잦은 읽기, process 쪽으로의 복사가 함께 겹쳐 충분히 빠르지 않았습니다. “메모리에 있다”와 “복사 비용이 없다”는 같은 말이 아닙니다.

ETS가 없앤 비용과 남긴 비용

이전: session process → ring process에 질문 → C port 기반 ring 조회 → 답장
ETS: session process → ETS에서 ring 직접 읽기 → caller process에서 lookup

C port가 ring을 제어하던 구조에서는 ring 값을 ETS에서 바로 읽기 어려워, Discord는 먼저 ring 구현을 pure Elixir로 바꿨습니다. 그 뒤 ring 값을 ETS에 넣고 다른 process가 직접 읽게 했습니다. 중앙 request/reply는 줄었지만, ETS에서 꺼낸 큰 Erlang term은 읽는 process의 heap으로 복사됩니다. ring 자체가 컸기 때문에 이 메모리 복사가 lookup 비용의 큰 부분을 차지했습니다.

핵심 구분: 저장 위치와 읽은 뒤의 소유권 ETS가 같은 VM 안의 메모리에 있다는 사실만으로 모든 process가 같은 객체를 그대로 참조하는 것은 아닙니다. 이 사례에서 필요한 것은 빠른 table보다 “큰 값을 caller heap으로 반복 복사하지 않는 읽기 경로”였습니다.
비유 실제 사실 주의

4. 읽는 길 바꾸기

FastGlobal은 큰 지도를 함께 보게 했어요

FastGlobal은 Discord가 큰 hash ring을 빨리 읽기 위해 쓴 작은 Elixir 도구예요. 해시 알고리즘도, node를 새로 고르는 규칙도 아니에요. “거의 바뀌지 않는 큰 지도 하나를 VM 안에 읽기 전용으로 붙여 두고, 여러 process가 그 지도 자체를 함께 읽자”는 방법입니다.

먼저, FastGlobal이 정확히 한 일

1 · 무엇인가?

큰 값을 돌려주는 작은 helper

FastGlobal은 “현재 ring을 돌려줘”라고 답하는 함수가 든 module을 runtime에 만듭니다. 여기서 module은 BEAM VM이 실행할 수 있는 작은 코드 파일이에요.

2 · 무엇을 해결했나?

읽을 때의 대형 복사

ETS에서는 session process가 큰 ring을 꺼낼 때 자기 heap에 사본을 받았습니다. FastGlobal에서는 여러 process가 같은 읽기 전용 ring을 보고, 매번 자기 사본을 만들지 않습니다.

3 · 무엇을 포기했나?

ring을 고치는 일은 무거워짐

지도에 node 하나를 더하거나 빼려면, 기존 지도의 한 칸만 고치는 것이 아니라 새 ring이 든 module을 만들고 compile한 뒤 VM에 load해야 합니다.

큰 지도를 매번 복사

  • 읽을 때마다 큰 값이 process 쪽으로 옮겨집니다.
  • 학생 수가 늘수록 복사 일이 함께 늘어납니다.
  • ETS는 빠르지만 이 큰 값의 복사는 남습니다.

벽에 붙인 지도를 함께 보기

  • module의 constant pool(상수를 보관하는 곳)을 여러 process가 함께 읽는 shared heap처럼 활용합니다.
  • 각 process가 같은 큰 값을 복사 없이 읽습니다.
  • 읽는 일이 아주 많고 값 변경이 드문 상황에 잘 맞습니다.
대가를 학교 지도 비유로 정확히 말하면
ETS는 학생이 큰 지도를 볼 때마다 복사본을 한 장씩 받는 방식이에요. FastGlobal은 복사 대신 벽의 큰 지도를 함께 보므로 읽기는 가벼워집니다. 하지만 지도가 바뀌면 벽에 붙은 지도를 통째로 새로 인쇄해서 갈아 끼워야 해요. 즉, 매번 읽는 비용을 줄이는 대신, 드문 갱신 한 번의 비용을 더 크게 받아들인 선택입니다.

평소에 guild가 어느 node로 갈 때는 이렇게 읽어요

여기서 FastGlobal이 “guild:42는 node B야”라고 직접 결정하는 것은 아닙니다. FastGlobal의 역할은 현재 hash ring 지도를 복사 없이 꺼내 주는 것뿐이에요. 실제로 어느 node를 고르는 계산은 요청을 처리하는 process가 합니다.

요청을 처리하는 process
→ FastGlobal에 “현재 ring 지도 줘”라고 읽기 요청
→ 공유된 읽기 전용 ring을 큰 복사본 없이 받음
→ guild:42를 해시해 ring 위의 위치를 계산
→ 시계 방향으로 처음 만나는 node를 찾음
→ node B로 guild 생성 또는 메시지 전달

따라서 FastGlobal은 길 안내 책을 꺼내 주는 책장에 가깝고, 요청을 처리하는 process는 그 지도를 보고 실제 길을 고르는 사람에 가깝습니다. FastGlobal이 ring을 읽게 해 주어도 안정 해시의 “해시하기 → 시계 방향 첫 node 찾기” 규칙은 그대로예요.

그럼 ring이 바뀌는 날에는 누가 무엇을 하나요?

node가 추가되거나 빠지면, node 목록을 관리하는 쪽이 새 ring을 만듭니다. 그 뒤 FastGlobal에 새 지도를 넣어 달라고 요청합니다. 이때 FastGlobal은 ETS처럼 표의 한 칸을 바꾸는 방식이 아니라, 새 ring을 담은 새 module을 만들어 옛 module 대신 load합니다.

node 구성 변경 감지
→ 새 node 목록으로 새 ring 계산
→ 새 ring 값을 품은 FastGlobal module 생성
→ compile → BEAM VM에 load
→ 그 뒤의 요청 처리 process들은 새 ring을 읽음

이 작업에는 코드 생성과 compile, load가 필요하므로 매 요청마다 하기에는 너무 무겁습니다. 반대로 Discord의 ring은 읽는 횟수에 비해 바뀌는 횟수가 훨씬 적었어요. 그래서 “가끔 지도 전체를 교체하고, 평소에는 모두가 아주 빨리 읽기”가 이 사례에서는 이득이었습니다.

FastGlobal은 실제로 어떤 순서로 움직일까요?

처음 ring 만들기 또는 node 구성 변경
1. 새 node 목록으로 새 ring을 계산
2. 그 새 ring을 돌려주는 module을 runtime에 생성
3. module을 compile하고 BEAM VM에 load
4. 이후 session process들은 그 module을 호출해 같은 읽기 전용 ring을 바로 읽음

아이디어의 출발점은 mochiglobal이었습니다. Discord는 이를 Elixir로 옮기면서 값을 등록할 때 atom을 계속 새로 만들지 않도록 기능을 보강했고, 그 구현을 FastGlobal이라고 이름 붙였습니다. 여기서 중요한 점은 ring을 제자리에서 수정하는 공유 변수가 아니라는 거예요. ring이 바뀌면 새 module로 교체합니다. 그래서 설정처럼 읽기는 매우 많고 변경은 드문 큰 값에는 알맞지만, 사용자 상태처럼 초마다 바뀌는 데이터에는 맞지 않습니다.

정확한 결론 핵심 개선은 “어떤 node가 맡을지 정하는 배치 규칙(placement policy)”을 완전히 바꾼 일이 아닙니다. ring의 저장·조회 경로를 단일 process와 ETS 복사에서 공유 read-only 접근으로 최적화한 일입니다. C port 구현을 pure Elixir로 바꾼 일도 있으므로 “알고리즘은 문자 그대로 아무것도 바뀌지 않았다”고 단정하지 않습니다.
계산값 주의

5. 구조로 비교하기

읽는 길을 바꾸면 줄이 사라져요

같은 ring을 읽더라도 누가 어떤 방식으로 읽는지에 따라 병목이 달라집니다. 아래 그림은 특정 장비의 벤치마크 숫자가 아니라, 세 가지 읽기 구조의 차이를 비교합니다.

비유 실제 사실 주의

6. 빨라진 뒤의 새 문제

앞길을 뚫자, 다음 문 앞에 새 줄이 생겼어요

FastGlobal 덕분에 remote Erlang node를 빨리 찾자, 이번에는 그 뒤 단계인 guild_pid lookup에 요청이 한꺼번에 몰렸습니다. 느렸던 앞길이 뜻밖에 속도 조절 장치처럼 작동하고 있었던 거예요.

1단계 · 앞길이 빨라짐

session들이 바로 다음 문으로 갔어요

거의 500만 session process가 guild node 쪽의 registry process 열 개로 빠르게 향했습니다.

2단계 · 새 줄이 생김

시간 초과와 재시도가 줄을 더 키웠어요

끝난 줄 알았던 요청도 queue에 남고 다시 시도되어, message queue와 메모리가 계속 커질 수 있었습니다.

3단계 · 입장표를 둠

semaphore가 동시에 들어가는 요청 수를 제한했어요

자리가 꽉 차면 실패할 요청을 미리 돌려보내, registry가 감당할 수 있는 만큼만 통과시켰습니다.

실제 구현 Discord는 ETS의 :ets.update_counter/4로 숫자를 원자적으로 조건부 증가시키고, write_concurrency를 사용해 Semaphore 라이브러리의 바탕을 만들었습니다. 학교 비유로는 “남은 입장표가 있을 때만 한 장 가져가기”와 비슷합니다.
두 lookup을 섞지 않기 앞에서 FastGlobal이 빠르게 만든 것은 ring을 읽어 remote node를 찾는 단계입니다. semaphore가 보호한 것은 그다음 guild_pid를 찾는 단계입니다. semaphore가 안정 해시나 FastGlobal을 대신한 것은 아닙니다.

timeout이 났는데도 왜 queue가 계속 커졌을까요?

순서 session 쪽 guild registry 쪽
1. 요청 guild PID를 찾는 call을 보냄 요청이 mailbox 뒤에 쌓임
2. timeout 기다리기를 포기하고 실패로 판단 이미 보낸 요청은 자동 취소되지 않아 queue에 남을 수 있음
3. retry backoff 뒤에 같은 종류의 요청을 다시 보냄 옛 요청 위에 새 요청까지 더해져 회복보다 유입이 빨라짐
4. 연쇄 장애 기다리는 동안 다른 서비스의 메시지도 mailbox에 축적 메모리 사용량이 커지고 VM 전체가 OOM에 이를 수 있음
semaphore의 역할은 더 빨리 처리하는 것이 아니에요 처리 가능한 수보다 요청이 많을 때 일부를 입구에서 빠르게 실패시켜, registry의 queue가 회복 불가능한 크기로 자라는 것을 막았습니다. 이는 처리량 최적화라기보다 overload protection과 backpressure 설계입니다.
비유 실제 사실

7. 전후 한눈에 보기

세 단계에서 비용의 위치가 달라졌어요

비교할 것 처음: ring process 중간: ETS 최종: FastGlobal
요청 경로 session → ring process → C port session process가 ETS를 직접 읽음 session process가 runtime module을 직접 호출
주요 비용 process 왕복과 한 mailbox의 중앙 queue 큰 ring을 caller heap으로 복사 공유 상수 lookup이라 읽을 때 복사하지 않음
읽는 방식 한 process에 질문하고 답을 받음 각 process가 ETS를 직접 읽음 공유 상수를 복사 없이 읽음
대가 burst 때 중앙 처리량에 묶임 ring 소유 process가 ETS 사본을 계속 갱신 node 변경 때 새 ring 계산 → module 생성 → compile → load가 필요함
실제 사실

8. 비유를 실제 시스템으로 바꾸기

학교 지도 속 역할은 실제로 무엇일까요?

지금까지의 학교 비유를 실제 2017년 Discord 흐름으로 다시 연결해 봅시다.

실제 요청 경로

WebSocket → session GenServer → guild 같은 entity의 remote Erlang node를 ring에서 조회 → 해당 node의 guild GenServer와 통신

초기 ring 조회는 session process가 request/reply로 ring 제어 Erlang process에 묻고, 그 process가 C port 기반 hash ring에서 remote node를 찾아 돌려주는 경로였습니다.

FastGlobal은 runtime에 정적 값을 반환하는 module을 compile/load하고, caller가 그 값을 읽게 했습니다. 이 덕분에 큰 ring을 process마다 반복 복사하지 않았습니다.

설계 원리 주의

9. 사례에서 꺼낸 설계 원리

Discord만의 문제가 아니라, 시스템 설계 문제예요

이 사례의 값은 FastGlobal이라는 도구 이름을 외우는 데 있지 않습니다. 부하가 커질 때 어디서 queue가 생기고, 최적화 뒤의 다음 병목을 어떻게 예측할지 배우는 데 있습니다.

원리 1 · hot path

작은 비용도 호출 횟수와 곱해져요

작은 비용도 호출이 반복되면 커집니다. 평균 지연만 보지 말고 burst 때 요청이 어느 줄에 쌓이는지 먼저 봐야 합니다.

원리 2 · serialization

공유 상태의 주인 하나가 직렬화 지점이 될 수 있어요

process가 가볍다는 사실과 한 process가 무한한 처리량을 가진다는 말은 다릅니다. mailbox 한곳에 모이면 그곳이 상한선입니다.

원리 3 · data shape

도구보다 데이터의 읽기·쓰기 비율을 먼저 봐요

ring은 크고, 읽기는 매우 많고, 변경은 드물었습니다. 그래서 느린 갱신과 빠른 공유 읽기의 교환이 성립했습니다.

원리 4 · backpressure

앞단의 느림이 우연한 보호막일 수도 있어요

node lookup을 빠르게 하자 뒤의 registry가 무너졌습니다. 한 단계를 최적화하면 다음 단계가 같은 유입량을 버틸지 다시 계산해야 합니다.

원리 5 · overload protection

늦은 성공보다 빠른 실패가 시스템을 살릴 때가 있어요

이미 성공할 수 없는 요청을 queue에 넣지 않으면 메모리와 retry 폭증을 막고, 정상 요청이 회복할 공간을 남길 수 있습니다.

다른 시스템에 그대로 복사하지 않기 FastGlobal이 항상 ETS보다 낫다는 결론은 아닙니다. 데이터가 자주 바뀌거나 작다면 ETS가 더 단순하고 알맞을 수 있습니다. 먼저 값의 크기, 변경 빈도, 읽기 횟수, 복사 비용, 실패 시 queue 동작을 측정해야 합니다.

10. 용어 사전

낯선 말을 짧게 정리해요

guild
Discord 안의 커뮤니티 서버를 뜻하는 이름입니다.
session process
접속한 사용자 한 명의 연결과 활동을 담당하는 process입니다.
Erlang node
여러 Erlang process가 실행되는 runtime 단위입니다.
lookup
key를 보고 담당 위치나 값을 찾아보는 일입니다.
consistent hash ring
key와 node를 둥근 공간에 놓아 담당 node를 고르는 규칙입니다.
request/reply
다른 process에 질문을 보내고 답을 기다리는 통신 방식입니다.
ETS
Erlang VM이 제공하는 빠른 in-memory table입니다.
FastGlobal
Discord가 쓴 Elixir helper입니다. 거의 변하지 않는 큰 값을 읽기 전용으로 공유해, 읽을 때마다 각 process에 큰 사본을 만들지 않게 합니다. 대신 값이 바뀌면 새 module을 만들어 교체해야 합니다.
hot path
시스템에서 아주 자주 실행되어 속도에 큰 영향을 주는 길입니다.
read-only
여러 곳에서 읽지만 자주 바꾸지는 않는 상태를 뜻합니다.
semaphore
동시에 들어갈 수 있는 요청 수를 입장표처럼 제한하는 장치입니다.
mailbox
Erlang process가 받은 메시지를 처리하기 전까지 순서대로 보관하는 queue입니다.
backpressure
뒤 단계가 감당할 수 있도록 앞 단계의 요청 속도나 수를 조절하는 압력입니다.
PID
실행 중인 Erlang process를 가리키는 식별자입니다.
C port
Erlang VM이 외부 C 코드와 통신하도록 연결하는 경계입니다.
OOM
메모리가 부족해져 process나 VM이 정상적으로 동작할 수 없는 상태입니다.
