# 뉴스 피드 시스템 설계

11장을 그냥 기능만 보면 **뉴스 피드 만들기**다.

그런데 시스템 설계 관점에서 보면 핵심은 조금 다르다.

> 뉴스 피드를 만드는 비용을 글을 쓸 때 낼 것인가, 피드를 읽을 때 낼 것인가?

이 선택에 따라 전체 구조가 달라진다.

- 읽을 때 만든다: Fan-out on Read, Pull
- 쓸 때 미리 만든다: Fan-out on Write, Push
- 사용자 규모에 따라 둘을 섞는다: Hybrid

결국 이 장은 기능보다 **읽기 비용과 쓰기 비용을 어디에 둘 것인지**를 배우는 장이다.

---

## 1. 요구사항 정리

- DAU 1,000만 명
- 사용자 한 명의 친구 수는 최대 5,000명
- 사용자는 새 글을 작성할 수 있음
- 사용자는 친구들이 작성한 글을 뉴스 피드에서 볼 수 있음
- 뉴스 피드는 최신 글부터 시간 역순으로 정렬
- 텍스트, 이미지, 동영상 지원
- 웹과 모바일 지원

이번 설계에서는 추천 점수나 광고 랭킹은 제외한다.

정렬 기준은 단순하게 최신순으로 잡는다.

그러면 핵심 기능은 두 개다.

```http
POST /v1/posts
GET  /v1/feed
```

글 작성 요청은 대략 이런 형태다.

```http
POST /v1/posts
```

```json
{
  "content": "hello",
  "media_ids": ["img_123"]
}
```

피드 조회는 커서와 조회 개수를 받는다.

```http
GET /v1/feed?cursor=xxx&limit=20
```

페이지 번호보다 커서를 쓰는 이유는 피드 앞쪽에 새 글이 계속 추가되기 때문이다.

페이지 번호를 사용하면 조회 사이에 새 글이 들어왔을 때 같은 글을 다시 보거나 일부 글을 건너뛸 수 있다.

---

## 2. 처음에는 가장 단순하게 만든다

처음부터 Redis나 Kafka를 붙일 필요는 없다.

가장 단순한 구조는 아래와 같다.

```text
User
 ↓
Web Server
 ↓
Post DB
```

사용자가 글을 작성하면 `posts` 테이블에 저장한다.

```text
posts

id | user_id | content | created_at
------------------------------------
1  | A       | hello   | 10:00
2  | B       | hi      | 10:01
```

사용자 A가 피드를 조회하면 서버는 다음 순서로 처리한다.

1. A의 친구 목록을 조회한다.
2. 친구들의 사용자 ID를 얻는다.
3. 친구들이 작성한 글을 조회한다.
4. 최신순으로 정렬한다.
5. 상위 20개를 반환한다.

SQL로 단순하게 표현하면 이런 형태다.

```sql
SELECT *
FROM posts
WHERE user_id IN (친구 5000명)
ORDER BY created_at DESC
LIMIT 20;
```

작은 서비스라면 이 구조로도 충분하다.

글을 작성할 때 DB에 한 번만 저장하면 되고, 피드를 조회할 때 항상 현재 친구 관계를 기준으로 글을 가져올 수 있다.

문제는 사용자와 게시물이 많아졌을 때 발생한다.

---

## 3. 피드를 읽을 때마다 만들면 어떻게 될까?

사용자 A가 5,000명의 친구를 가지고 있다고 해보자.

```text
B
C
D
E
...
5,000명
```

A가 피드를 열 때마다 서버는 친구들의 글을 모아야 한다.

```text
B의 글 조회 ─┐
C의 글 조회 ─┤
D의 글 조회 ─┤
...          ├→ merge → sort → 상위 20개 반환
5,000명       ┘
```

이 방식을 **Fan-out on Read** 또는 **Pull 모델**이라고 한다.

정확히 말하면 피드를 읽는 시점에 필요한 게시물을 모아서 피드를 만든다.

### Pull의 장점

글 작성이 싸다.

```text
사용자 글 작성
   ↓
posts DB 저장
   ↓
끝
```

게시물은 한 번만 저장하면 된다.

친구 관계가 바뀌어도 별도의 피드 데이터를 수정할 필요가 없다.

조회 시점의 친구 목록을 사용하기 때문에 항상 현재 관계가 반영된다.

### Pull의 단점

피드 조회가 비싸다.

최종적으로 반환하는 글은 20개지만 그 20개를 찾기 위해 훨씬 많은 게시물을 확인해야 할 수 있다.

```text
친구 100명   → 후보 게시물 2,000개
친구 1,000명 → 후보 게시물 20,000개
친구 5,000명 → 후보 게시물 100,000개
```

`LIMIT 20`이 있다고 해서 후보 게시물 조회와 정렬 비용까지 사라지는 것은 아니다.

실험에서도 팔로잉 수가 늘어날수록 Pull 피드의 p95가 증가했다.

```text
팔로잉 100명   → 13.80ms
팔로잉 1,000명 → 38.88ms
팔로잉 5,000명 → 120.06ms
```

팔로잉 수는 50배가 되었고 p95는 약 8.7배 증가했다.

여기서 확인할 수 있는 것은 하나다.

> Pull의 읽기 비용은 최종 반환 개수보다 조회해야 하는 후보 집합의 크기에 더 크게 영향을 받는다.

---

## 4. 그러면 피드를 미리 만들어두면 된다

Pull의 문제는 피드를 요청할 때마다 같은 계산을 반복한다는 것이다.

그러면 반대로 사용자가 글을 작성했을 때 친구들의 피드에 미리 넣어둘 수 있다.

```text
A가 글 작성
    ↓
A의 친구 목록 조회
    ↓
B의 Feed Cache에 추가
C의 Feed Cache에 추가
D의 Feed Cache에 추가
...
```

예를 들면 아래와 같다.

```text
Feed:B = [A-post-101, ...]
Feed:C = [A-post-101, ...]
Feed:D = [A-post-101, ...]
```

이제 B가 피드를 요청하면 친구들의 글을 다시 모을 필요가 없다.

```text
B의 피드 요청
      ↓
Feed Cache 조회
      ↓
이미 정렬된 목록 반환
```

이 방식을 **Fan-out on Write** 또는 **Push 모델**이라고 한다.

### 왜 Fan-out이라고 부를까?

`fan-out`은 하나의 입력이 여러 대상으로 퍼지는 구조를 말한다.

```text
                 ┌→ B feed
                 │
                 ├→ C feed
A의 새 게시물 ────┼→ D feed
                 │
                 ├→ E feed
                 │
                 └→ F feed
```

하나의 게시물 이벤트가 여러 사용자 피드로 퍼지기 때문에 fan-out이다.

Pull과 Push를 비용 기준으로 비교하면 아래와 같다.

```text
Fan-out on Read
- 쓰기 쌈
- 읽기 비쌈

Fan-out on Write
- 쓰기 비쌈
- 읽기 쌈
```

Push는 비용을 없애는 방식이 아니다.

읽을 때 하던 계산을 글을 작성한 이후로 옮기는 방식이다.

## 5. Push 작업은 HTTP 요청과 분리한다

Push를 사용한다고 해서 사용자의 글 작성 요청 안에서 친구 5,000명의 피드를 모두 수정하면 안 된다.

아래처럼 처리하면 사용자는 fan-out이 끝날 때까지 기다려야 한다.

```text
POST 요청
   ↓
Post DB 저장
   ↓
친구 5,000명의 피드 수정
   ↓
전부 완료
   ↓
200 OK
```

친구가 많을수록 글 작성 응답도 느려진다.

그래서 사용자 요청과 fan-out 작업을 분리한다.

```text
POST 요청
   ↓
Post DB 저장
   ↓
Queue에 이벤트 저장
   ↓
200 OK
```

실제 fan-out은 별도의 worker가 처리한다.

```text
Queue
  ↓
Fan-out Worker
  ↓
친구 목록 조회
  ↓
각 사용자의 Feed Cache 갱신
```

전체 쓰기 흐름은 대략 아래와 같다.

```text
Client
  ↓ POST
Web Server
  ↓
Post Service
  ├→ Post DB
  └→ Message Queue
          ↓
     Fan-out Workers
          ↓
     Friends Service
          ↓
     Feed Cache B, C, D ...
```

여기서 Kafka나 Redpanda 같은 메시지 큐를 사용할 수 있다.

사용자가 기다리는 것은 게시물 원본이 정상적으로 저장되는 시점까지다.

친구의 피드에 노출되는 작업은 백그라운드에서 완료된다.

즉 짧은 노출 지연을 허용하는 최종적 일관성 구조다.

## 6. DB 저장과 이벤트 발행 사이의 문제

게시물 저장과 Queue 이벤트 발행을 따로 처리하면 애매한 구간이 생긴다.

```text
Post DB 저장 성공
      ↓
프로세스 장애
      ↓
Queue 이벤트 발행 실패
```

게시물은 저장되었는데 fan-out 이벤트가 없기 때문에 친구 피드에는 나타나지 않는다.

이 문제를 줄이기 위해 **Transactional Outbox**를 사용할 수 있다.

```text
하나의 DB 트랜잭션
  ├→ posts 저장
  └→ outbox 이벤트 저장
```

트랜잭션이 성공하면 게시물과 발행할 이벤트가 함께 남는다.

별도의 relay가 아직 발행되지 않은 outbox 이벤트를 Queue로 전송한다.

```text
Post Service
  ↓
PostgreSQL
  ├→ posts
  └→ outbox
         ↓
    Outbox Relay
         ↓
      Redpanda
         ↓
    Fan-out Worker
```

이렇게 하면 DB 저장과 이벤트 발행을 완전히 같은 작업으로 만들 수는 없어도, 이벤트가 조용히 사라지는 구간을 줄일 수 있다.

## 7. Feed Cache에는 무엇을 저장할까?

여기서 게시물 전체를 모든 친구의 피드에 복사하면 안 된다.

```json
{
  "user": {
    "id": "A",
    "name": "철수"
  },
  "content": "hello",
  "image": "..."
}
```

이 객체를 친구 5,000명의 피드에 그대로 넣으면 같은 본문과 사용자 정보가 5,000번 복사된다.

게시물이 수정될 때 5,000개의 복사본을 어떻게 갱신할지도 문제가 된다.

그래서 Feed Cache에는 보통 게시물 전체가 아니라 **post ID만 저장한다.**

```text
Feed:user_123

[
  post_99342,
  post_99340,
  post_99301
]
```

피드를 읽을 때는 먼저 post ID 목록을 얻고 실제 게시물은 Post Cache나 Post DB에서 가져온다.

```text
User Feed
   ↓
[post_923, post_901, post_881]
   ↓
Post Cache / Post DB
   ↓
실제 게시물 객체
```

이를 hydrate 과정이라고 볼 수 있다.

피드 인덱스는 **어떤 글을 어떤 순서로 보여줄지**만 알고, 실제 게시물 내용은 원본 저장소에서 가져온다.

---

## 8. 글은 한 번 저장하는데 사용자별 피드는 왜 따로 저장할까?

처음 보면 이상해 보일 수 있다.

```text
Post DB에는 글을 한 번 저장
Redis에는 사용자별 Feed 저장
```

결국 같은 데이터를 중복해서 저장하는 것처럼 보인다.

그런데 두 저장소에 들어가는 데이터의 역할이 다르다.

### Post DB

게시물의 실제 원본이다.

```text
post_101
- author_id: A
- content: hello
- media_key: img_123
- created_at: 10:00
```

본문 수정이나 삭제의 기준은 Post DB다.

### Feed Cache

사용자별 조회를 빠르게 하기 위한 인덱스다.

```text
feed:B = [post_101, ...]
feed:C = [post_101, ...]
feed:D = [post_101, ...]
```

여기에는 본문이 아니라 post ID와 정렬에 필요한 정보만 있다.

정리하면 아래와 같다.

```text
Post DB
  = 무엇이 사실인가
  = Source of Truth

Feed Cache
  = 누구에게 어떤 순서로 보여줄 것인가
  = 조회용 Projection / Index
```

그래서 사용자별 Feed Cache는 게시물 원본을 복제한 것이 아니다.

읽기 성능을 위해 같은 post ID를 여러 사용자 인덱스에 투영한 것이다.

이 구조는 몇 가지 장점이 있다.

- 게시물 본문은 한 곳에서 관리한다.
- 본문이 수정되어도 모든 사용자 피드를 수정할 필요가 없다.
- Redis 데이터가 사라져도 Post DB를 기준으로 다시 만들 수 있다.
- Feed Cache의 보관 길이를 제한할 수 있다.
- 사용자별 피드 조회는 이미 정렬된 post ID만 읽으면 된다.

즉 **도메인 데이터의 중복 저장**과 **조회 인덱스의 의도된 중복**은 다르다.

이 차이를 이해하면 Feed Cache 구조가 자연스럽게 이해된다.

## 9. Redis가 Feed Cache에 잘 맞는 이유

뉴스 피드는 다음 특징을 가진다.

- 최신 데이터가 중요함
- 게시물 순서가 중요함
- 읽기 요청이 많음
- 과거 전체 피드를 항상 메모리에 둘 필요는 없음
- 사용자별로 일정 개수만 빠르게 조회하면 됨

그래서 Redis의 Sorted Set 같은 자료 구조가 잘 맞는다.

개념적으로는 아래와 같다.

```text
key: feed:user_123

score        value
--------------------
1725512031   post_941
1725512012   post_932
1725511999   post_921
```

score에 timestamp를 사용하면 최신순 조회가 쉽다.

```text
ZREVRANGE feed:user_123 0 19
```

최신 post ID 20개를 가져온 뒤 실제 게시물 객체를 조회하면 된다.

다만 timestamp만 정렬 기준으로 사용하면 같은 시간에 생성된 게시물의 순서가 애매해질 수 있다.

그래서 커서는 아래 두 값을 같이 사용하는 것이 안전하다.

```text
(created_at, post_id)
```

`created_at`이 같으면 `post_id`로 순서를 결정한다.

다음 페이지는 이전 페이지의 마지막 커서보다 작은 항목부터 조회한다.

```text
1페이지 마지막 항목
(10:01:00, post_101)

2페이지 시작 조건
< (10:01:00, post_101)
```

이렇게 하면 새 게시물이 앞에 추가되어도 페이지 사이의 중복과 누락을 줄일 수 있다.

## 10. Push에도 큰 문제가 있다

일반 사용자는 친구나 팔로워가 수백 명 정도라서 Push가 잘 동작할 수 있다.

그런데 팔로워가 아주 많은 사용자는 다르다.

```text
Taylor Swift
followers = 300,000,000
```

글 하나를 작성할 때 모든 팔로워의 Feed Cache를 수정하면 아래 작업이 필요하다.

```text
게시물 1개
   ↓
3억 개 Feed Cache 갱신
```

비동기로 처리해도 총 작업량이 사라지는 것은 아니다.

Queue가 밀릴 수 있고 Redis 쓰기 처리량과 메모리 사용량도 커진다.

로컬 실험에서도 게시물 하나가 100,000명의 피드로 전파되었다.

```text
POST 응답              4.77ms
fan-out 완료           756ms
Redis 쓰기             100,000회
Redis 메모리 사용량    약 12.24MB
```

API 응답은 4.77ms로 빠르다.

하지만 백그라운드에서는 100,000번의 쓰기가 발생했다.

여기서 중요한 것은 이것이다.

> 비동기 처리는 사용자의 대기 시간을 줄여주지만 전체 시스템의 작업량까지 줄여주지는 않는다.

이게 Fan-out on Write의 핵심 약점이다.

## 11. 그래서 Hybrid를 사용한다

일반 사용자와 유명 사용자를 같은 방식으로 처리할 필요는 없다.

```text
일반 사용자
    ↓
Fan-out on Write

유명 사용자
    ↓
Fan-out on Read
```

내가 아래 사용자를 팔로우한다고 해보자.

```text
철수
영희
민수
Taylor Swift
```

일반 사용자의 게시물은 내 Feed Cache에 미리 들어온다.

```text
my_feed

철수 post
민수 post
영희 post
```

Taylor Swift처럼 팔로워가 많은 사용자의 게시물은 내 Feed Cache에 Push하지 않는다.

내가 피드를 조회할 때 대형 사용자의 게시물을 별도로 가져온다.

```text
미리 만들어둔 Push Feed
            +
대형 사용자의 최신 게시물 Pull
            ↓
          merge
            ↓
          sort
            ↓
         top 20
```

구조로 보면 아래와 같다.

```text
           Push Feed
               │
               ▼
           ┌───────┐
           │ Merge │ → 정렬 → 중복 제거 → Client
           └───────┘
               ▲
               │
       Celebrity Posts
              Pull
```

이 방식을 **Hybrid Fan-out**이라고 한다.

프로젝트에서는 팔로워 100,000명을 실험용 기준으로 사용했다.

```text
followers < 100,000
→ Push

followers >= 100,000
→ Pull
```

하지만 100,000이라는 숫자가 정답은 아니다.

실제 기준은 아래 값을 보고 다시 정해야 한다.

- 사용자의 글 작성 빈도
- 실제로 피드를 읽는 활성 팔로워 비율
- 허용 가능한 피드 노출 지연
- Queue 처리량
- Redis 쓰기 비용과 메모리 비용

팔로워가 많아도 글을 거의 작성하지 않는 사용자라면 Push가 더 나을 수 있다.

반대로 팔로워가 아주 많고 글도 자주 작성한다면 Pull이 더 유리할 수 있다.

## 12. Hybrid라고 무조건 빠른 것은 아니다

구조를 Hybrid로 바꿨다고 자동으로 성능이 좋아지는 것은 아니다.

처음 구현에서는 게시물마다 작성자의 follower count를 확인했다.

```text
게시물 조회
   ↓
각 게시물 작성자의 follower count 조회
   ↓
대형 사용자인지 판단
```

이 방식은 게시물 수만큼 상관 서브쿼리가 반복될 수 있다.

초기 Hybrid 실험의 p95는 31.68ms였다.

이후 대형 작성자 목록을 먼저 구하고 그 작성자들의 게시물만 조인하도록 변경했다.

```text
follows GROUP BY followee_id
          ↓
HAVING follower_count >= threshold
          ↓
대형 작성자 목록
          ↓
posts 조인
```

개선 후 p95는 7.85ms까지 내려갔다.

```text
초기 Hybrid p95   31.68ms
개선 후 p95        7.85ms
```

여기서 얻을 수 있는 결론은 아래와 같다.

> 아키텍처 방향이 맞아도 실제 데이터 접근 경로와 쿼리가 나쁘면 느리다.

전략 선택과 쿼리 검증은 따로 해야 한다.

## 13. Pull, Push, Hybrid 읽기 성능 비교

같은 부하 조건에서 세 전략을 비교한 결과는 아래와 같다.

```text
Pull     p95 14.87ms
Push     p95  7.16ms
Hybrid   p95  7.85ms
```

Push는 Pull보다 읽기 p95가 절반 정도로 줄었다.

Hybrid도 Push에 가까운 읽기 성능을 보였다.

하지만 이 결과만 보고 Push가 무조건 좋다고 결론내리면 안 된다.

각 전략이 부담하는 비용이 다르기 때문이다.

| 전략 | 쓰기 비용 | 읽기 비용 | 추가 책임 |
| --- | --- | --- | --- |
| Pull | 낮음 | 높음 | 관계 조인, 후보 정렬 |
| Push | 높음 | 낮음 | Queue, Redis, 재처리, 저장 증폭 |
| Hybrid | 중간 | 중간 | 두 결과의 병합과 임계값 관리 |

성능 수치는 읽기 경로만 보여준다.

실제 의사결정에서는 쓰기 증폭, 저장 비용, 장애 복구까지 같이 봐야 한다.

## 14. 친구 관계가 바뀌면 어떻게 할까?

Push 방식에서는 친구 관계가 바뀐 뒤에도 이전 post ID가 Feed Cache에 잠시 남을 수 있다.

예를 들어 아래 상황이다.

```text
t1: A의 글이 B의 피드에 Push됨
t2: B가 A를 unfollow함
t3: Redis에는 A의 post ID가 아직 남아 있음
```

Redis에 값이 있다고 그대로 반환하면 B는 더 이상 팔로우하지 않는 A의 글을 볼 수 있다.

그래서 읽기 시점에 현재 친구 관계를 다시 확인한다.

```text
Feed Cache에서 post ID 조회
           ↓
현재 follows 관계 확인
           ↓
볼 수 없는 게시물 제거
           ↓
부족하면 다음 Redis 구간 추가 조회
```

여기서 중요한 기준은 아래와 같다.

```text
Redis Feed Cache
= 성능을 위한 Projection

Follow DB
= 현재 관계의 Source of Truth
```

캐시는 권한의 원본이 아니다.

최종 노출 여부는 현재 친구 관계를 기준으로 결정해야 한다.

## 15. 실패와 재처리는 어떻게 처리할까?

Fan-out Worker가 100,000명의 피드를 수정하다가 중간에 죽을 수 있다.

```text
100,000개 작업 시작
      ↓
5,122개 처리
      ↓
Worker 장애
```

이때 메시지를 이미 처리했다고 표시하면 나머지 사용자의 피드는 영원히 갱신되지 않는다.

그래서 Redis 쓰기가 성공한 뒤 Queue offset을 commit한다.

Worker가 중간에 죽으면 같은 이벤트를 다시 처리할 수 있다.

```text
이벤트 수신
   ↓
Redis Feed 갱신
   ↓
성공 확인
   ↓
offset commit
```

같은 이벤트가 다시 처리될 수 있으므로 작업은 멱등해야 한다.

Redis Sorted Set에 같은 post ID를 다시 `ZADD`해도 동일 member가 중복으로 추가되지는 않는다.

실패 실험에서는 아래와 같이 복구되었다.

```text
Worker 중단 시점
- 5,122 keys
- consumer lag 1

Worker 재시작 후
- 100,000 keys
- consumer lag 0
- 중복 Feed 항목 없음
```

정확히 한 번 처리했다고 주장하기보다 아래 구조를 선택한 것이다.

```text
At-least-once delivery
          +
Idempotent projection
          ↓
같은 최종 결과로 수렴
```

## 16. Redis가 전부 사라지면 어떻게 할까?

Feed Cache는 원본이 아니기 때문에 다시 만들 수 있어야 한다.

```text
Redis 전체 유실
      ↓
PostgreSQL의 posts 조회
      ↓
fan-out 이벤트 재생성
      ↓
Feed projection 복구
```

실험에서는 PostgreSQL 원본을 replay해서 100,000개의 projection을 다시 만들었다.

이 복구가 가능한 이유는 게시물 원본을 Redis에만 저장하지 않았기 때문이다.

```text
PostgreSQL
= 복구 기준이 되는 원본

Redis
= 없어져도 다시 만들 수 있는 조회 인덱스
```

현재 구현의 rebuild는 쓰기를 잠시 멈추는 오프라인 방식이다.

운영 환경에서는 다음 문제도 추가로 고민해야 한다.

- rebuild 중 들어오는 새 글 처리
- 특정 사용자 피드만 부분 복구
- Queue lag 모니터링
- 실패 이벤트를 보관할 DLQ
- 재시도 횟수와 backoff

## 17. 이미지와 동영상은 어디에 저장할까?

이미지와 동영상 바이트를 Post DB에 직접 넣을 필요는 없다.

대용량 파일은 Object Storage에 저장하고 CDN으로 전달한다.

```text
Image / Video Upload
        ↓
Object Storage
        ↓
CDN
        ↓
Client
```

예를 들면 아래와 같은 조합이다.

```text
S3
 ↓
CloudFront
```

Post DB에는 실제 파일 대신 object key나 URL처럼 파일을 찾기 위한 값만 저장한다.

```text
posts
- id
- user_id
- content
- created_at

post_media
- post_id
- object_key
- media_type
```

이렇게 하면 게시물 메타데이터 조회와 대용량 파일 전달을 분리할 수 있다.

## 18. 전체 뉴스 피드 구조

지금까지의 내용을 합치면 전체 구조는 아래와 같다.

```text
                         ┌───────────────┐
                         │    Client     │
                         └───────┬───────┘
                                 │
                         ┌───────▼───────┐
                         │ Load Balancer │
                         └───────┬───────┘
                                 │
                    ┌────────────▼────────────┐
                    │       Web Servers       │
                    └─────────┬───────┬───────┘
                              │       │
                         POST │       │ GET Feed
                              │       │
                ┌─────────────▼─┐   ┌─▼─────────────┐
                │ Post Service  │   │ Feed Service  │
                └───────┬───────┘   └──────┬────────┘
                        │                  │
              ┌─────────┴────────┐         ├→ Feed Cache
              ▼                  ▼         │
           Post DB            Queue        ├→ Post Cache / DB
                                 │         │
                                 ▼         └→ Celebrity Posts
                         Fan-out Workers
                                 │
                                 ▼
                          Friends Service
                                 │
                                 ▼
                            User Graph DB
```

쓰기 경로와 읽기 경로를 나누면 아래와 같다.

### 쓰기 경로

```text
Client
  ↓
Post Service
  ↓
Post DB + Outbox
  ↓
Queue
  ↓
Fan-out Worker
  ↓
Feed Cache
```

### 읽기 경로

```text
Client
  ↓
Feed Service
  ├→ 일반 사용자 Push Feed
  └→ 유명 사용자 Posts Pull
             ↓
       merge + sort + dedupe
             ↓
          post hydrate
             ↓
           Client
```

## 19. 이 장에서 이해해야 하는 핵심 개념

### 1. Fan-out on Read

```text
쓰기 쌈
읽기 비쌈
```

피드를 읽을 때 친구들의 게시물을 모은다.

### 2. Fan-out on Write

```text
쓰기 비쌈
읽기 쌈
```

글을 작성한 뒤 친구들의 피드를 미리 만든다.

### 3. Hybrid Fan-out

```text
일반 사용자 → Push
대형 사용자 → Pull
```

사용자 분포에 따라 읽기 비용과 쓰기 비용을 나눈다.

### 4. Cache와 Projection

```text
Post DB    → 게시물 원본
Feed Cache → 사용자별 post ID 인덱스
Post Cache → 게시물 객체 조회 가속
```

원본 데이터와 읽기 최적화 데이터를 분리한다.

### 5. Async Processing

```text
HTTP Request
     ↓
Post DB + Outbox
     ↓
Queue
     ↓
Worker
```

사용자 요청과 대량 fan-out 작업을 분리한다.

### 6. 멱등성과 복구

```text
At-least-once delivery
          +
Idempotent write
          ↓
재처리 가능한 시스템
```

Worker가 실패하거나 Redis가 사라져도 원본에서 다시 수렴할 수 있어야 한다.

## 20. 면접에서는 어떤 순서로 설명할까?

면접관이 뉴스 피드 시스템을 설계해보라고 했을 때 처음부터 Kafka와 Redis를 말하면 설명의 이유가 사라진다.

아래 순서로 병목을 따라가는 것이 중요하다.

```text
1. 요구사항 확인
        ↓
2. 대략적인 트래픽 계산
        ↓
3. API 정의
        ↓
4. 단순한 DB 기반 Pull 설계
        ↓
5. 문제 발견
   "피드 조회가 너무 비싸다"
        ↓
6. Fan-out on Write 도입
        ↓
7. Queue와 Worker로 비동기 처리
        ↓
8. 문제 발견
   "대형 사용자가 글을 쓰면 너무 비싸다"
        ↓
9. Hybrid Fan-out 도입
        ↓
10. Cache / Cursor / CDN 추가
        ↓
11. 일관성 / 장애 / 복구 논의
```

핵심은 **단순 설계 → 병목 발견 → 개선** 흐름이다.

기술을 많이 말하는 것보다 왜 다음 구조가 필요해졌는지 설명하는 것이 더 중요하다.

마지막에는 아래처럼 정리할 수 있다.

> 뉴스 피드 설계에는 항상 비용이 있다. Pull은 읽을 때 비용을 내고 Push는 쓸 때 비용을 낸다. Hybrid는 사용자 분포에 따라 그 비용을 나눈다. Post DB는 원본을 저장하고 Feed Cache는 사용자별 조회 인덱스를 저장한다. 그래서 글은 한 번만 저장하면서도 피드는 빠르게 읽을 수 있다.

이 문서의 실험은 전략별 비용의 방향을 확인하기 위한 로컬 실험이다.

- Apple M4 로컬 환경
- Docker VM 2 CPU / 약 1.9GiB
- 조건별 약 5초
- 약 50개 요청 단위

따라서 이 숫자를 운영 환경의 SLO나 서버 용량 산정 근거로 그대로 사용하면 안 된다.

실험에서 확인한 것은 절대적인 처리량이 아니라 아래 관계다.

```text
Pull
→ 후보 집합이 커질수록 읽기 비용 증가

Push
→ 읽기는 빨라지지만 팔로워 수만큼 쓰기 증폭

Hybrid
→ 대형 사용자의 쓰기 증폭을 읽기 비용으로 이동
```

결국 운영 환경에서는 실제 사용자 분포와 읽기·쓰기 비율을 측정한 뒤 전략과 임계값을 다시 결정해야 한다.
