# UUID

## 참고문헌

- 책의 참고 링크: [Universally unique identifier](https://en.wikipedia.org/wiki/Universally_unique_identifier)
- 현재 표준: [RFC 9562 - Universally Unique IDentifiers](https://www.rfc-editor.org/rfc/rfc9562)

## 무엇인가

UUID는 128비트 식별자다. 중앙 발급 서버나 전역 순번 저장소 없이 각 노드가 독립적으로 식별자를 만들 수 있다.

분산 시스템에서는 ID를 발급받기 위한 네트워크 호출이 없어도 된다는 점이 가장 큰 장점이다. ID 생성 서버가 단일 장애 지점이나 병목이 되지 않는다.

## 7장에서 검토한 이유

샤딩된 데이터베이스마다 `auto_increment`를 사용하면 서로 같은 숫자를 발급할 수 있다. UUID를 사용하면 데이터베이스 사이에서 순번을 조정하지 않고도 충돌 가능성이 극히 낮은 식별자를 만들 수 있다.

## 요구사항과 비교

| 요구사항 | 판단 | 이유 |
|---|---|---|
| 유일성 | 적합 | 중앙 조정 없이 각 노드가 독립적으로 생성 가능 |
| 숫자로만 구성 | 부적합 | 일반적인 표현은 하이픈을 포함한 16진 문자열 |
| 64비트 | 부적합 | UUID는 128비트 |
| 시간 순서 정렬 | 버전에 따라 다름 | UUIDv4는 무작위이고 UUIDv7은 시간 순서를 고려함 |
| 높은 처리량 | 적합 | 발급을 위해 중앙 서버에 요청할 필요가 없음 |

## UUID 버전에서 봐야 할 부분

### UUIDv4

- 무작위 값을 중심으로 생성한다.
- 생성 시각 순서와 정렬 순서가 일치하지 않는다.
- B-tree 계열 인덱스에 삽입 위치가 흩어질 수 있다.

### UUIDv7

- Unix epoch 기반 밀리초 타임스탬프를 상위 비트에 배치한다.
- 시간 순 정렬과 데이터베이스 인덱스 지역성을 개선한다.
- 2024년 RFC 9562에서 표준화됐다.
- 시간 정렬 문제는 개선하지만 128비트이므로 책의 64비트 조건은 여전히 만족하지 못한다.

## 책 내용과 현재 표준의 차이

책에서 UUID를 제외한 핵심 이유는 128비트 크기와 시간 순서 문제다. 현재는 UUIDv7이 시간 순서 문제를 상당 부분 보완했다. 따라서 지금 다시 설계한다면 다음처럼 판단해야 한다.

- 128비트를 허용하고 조정 없는 생성이 중요하면 UUIDv7을 검토한다.
- 반드시 64비트 숫자여야 하면 Snowflake 계열을 검토한다.

## 설계 시 질문

- 정말 64비트가 필수인가?
- 외부에 노출하는 ID와 데이터베이스 내부 기본 키를 같게 써야 하는가?
- 완전한 순서가 필요한가, 생성 시간 기준의 대략적인 정렬이면 충분한가?
- 인덱스 크기와 삽입 지역성이 중요한가?

## 핵심 정리

UUID는 분산 ID 생성에서 중앙 조정을 없애는 강력한 방법이다. 하지만 7장의 요구사항은 64비트 숫자이므로 최종안으로 선택되지 않는다. UUIDv7이 등장했다고 해서 이 크기 제약까지 해결된 것은 아니다.
