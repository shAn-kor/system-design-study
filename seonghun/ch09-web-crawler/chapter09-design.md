# 웹 크롤러

웹 크롤러는 시작 URL(seed URL)에서 페이지를 내려받고, 페이지 안의 링크를 찾아 다음 URL을 수집하는 작업을 반복한다. 겉보기에는 단순한 그래프 탐색이지만 실제 설계에서는 같은 URL을 여러 번 방문하지 않는 것, 특정 사이트에 요청이 몰리지 않게 하는 것, 실패한 요청을 다시 처리하는 것, JavaScript로 생성되는 콘텐츠를 읽는 것이 더 어렵다.

## 요구사항

### 기능 요구사항

- 시작 URL에서 웹페이지를 수집한다.
- 페이지의 링크를 추출하여 새로운 URL을 발견한다.
- 중복 URL과 중복 콘텐츠를 제거한다.
- `robots.txt`와 사이트별 요청 제한을 준수한다.
- 수집한 HTML과 메타데이터를 저장한다.
- 이미 수집한 페이지도 중요도와 변경 주기에 따라 다시 방문한다.
- 필요하면 JavaScript를 실행해야 보이는 SPA 콘텐츠도 수집한다.

### 비기능 요구사항

- **규모 확장성**: 크롤러 워커를 수평 확장할 수 있어야 한다.
- **안정성**: 네트워크 오류나 워커 장애가 전체 작업을 중단시키지 않아야 한다.
- **예절(politeness)**: 한 호스트에 과도한 요청을 보내지 않아야 한다.
- **효율성**: 중복 다운로드와 불필요한 브라우저 렌더링을 최소화해야 한다.
- **확장 가능성**: HTML 외의 다른 콘텐츠 형식이나 새로운 파서를 추가하기 쉬워야 한다.

## 개략적 규모 추정

다음은 설계를 구체화하기 위한 예시 값이다.

- 한 달에 10억 페이지 수집
- 평균 QPS: `10억 / 30일 / 24시간 / 3,600초 ≈ 386`
- 최대 QPS를 평균의 2배로 잡으면 약 770
- 페이지 하나의 평균 크기를 500KB로 잡으면 월 약 500TB
- 원본을 5년 보관하면 압축 전 약 30PB

실제 용량에는 이미지·동영상 포함 여부, 압축률, 렌더링 결과, 버전 보관 정책이 큰 영향을 준다. 따라서 페이지 수만으로 계산한 값은 저장소와 네트워크 대역폭의 하한에 가깝다.

## 전체 처리 흐름

1. 시작 URL을 URL 프런티어(frontier)에 넣는다.
2. 스케줄러가 지금 요청해도 되는 호스트의 URL을 선택한다.
3. DNS를 조회하고 해당 사이트의 `robots.txt` 규칙을 확인한다.
4. 다운로더가 페이지를 가져온다.
5. HTML 파서가 본문, 메타데이터, 링크를 추출한다.
6. 정적 HTML에 실제 콘텐츠가 없다면 렌더링 큐로 보내 JavaScript를 실행한다.
7. 콘텐츠 해시로 같은 내용을 이미 저장했는지 검사한다.
8. 새 콘텐츠는 저장하고, 새 링크는 정규화와 필터링을 거친다.
9. 방문 여부를 확인한 뒤 새로운 URL을 다시 프런티어에 넣는다.

| 구성 요소 | 역할 |
| --- | --- |
| Seed URL 저장소 | 크롤링을 시작할 신뢰할 수 있는 URL 보관 |
| URL 프런티어 | 방문할 URL의 우선순위와 실행 시각 관리 |
| 스케줄러 | 호스트별 요청 간격과 재시도 시점 결정 |
| DNS 캐시 | 반복되는 DNS 조회 비용 감소 |
| robots.txt 캐시 | 호스트별 접근 허용 규칙 보관 |
| HTML 다운로더 | HTTP 요청, 리디렉션, 압축, 타임아웃 처리 |
| 렌더러 | 격리된 헤드리스 브라우저에서 JavaScript 실행 |
| 파서 | 본문, 메타데이터, 링크 추출 |
| URL 필터 | 지원하지 않는 스킴, 파일 형식, 차단 경로 제거 |
| 방문 URL 저장소 | 같은 URL의 중복 방문 방지 |
| 콘텐츠 저장소 | 원본 응답과 정제된 결과 저장 |

## URL 프런티어

단순 FIFO 큐 하나만 사용하면 인기 사이트에서 발견한 URL이 큐를 가득 채워 한 호스트에 요청이 집중될 수 있다. 프런티어는 **중요도**와 **예절**을 함께 관리해야 한다.

### 우선순위

- 신뢰할 수 있는 시작 URL, 변경이 잦은 페이지, 상위 페이지에서 많이 연결된 URL에 높은 우선순위를 준다.
- 새 페이지 발견과 기존 페이지 재방문 작업이 서로 굶지 않도록 큐를 분리하거나 가중치를 둔다.
- 실패한 요청은 즉시 반복하지 않고 지수 백오프와 무작위 지연을 적용한다.

### 호스트별 요청 속도 제한

- URL을 `scheme + host + port` 기준으로 묶는다.
- 호스트별 대기 큐와 다음 요청 가능 시각을 저장한다.
- 같은 호스트에 동시에 보낼 수 있는 요청 수를 제한한다.
- `429 Too Many Requests`나 `Retry-After`를 받으면 해당 호스트의 다음 실행 시각을 늦춘다.
- 전역 QPS에 여유가 있더라도 호스트별 제한은 유지한다.

분산 환경에서는 호스트 해시를 기준으로 스케줄러 파티션을 나누면 여러 워커가 같은 호스트를 동시에 두드리는 문제를 줄일 수 있다.

## 중복 제거

### URL 중복

같은 페이지가 서로 다른 형태의 URL로 표현될 수 있으므로 방문 여부를 확인하기 전에 URL을 정규화한다.

- 호스트 이름을 소문자로 바꾼다.
- 기본 포트인 `:80`, `:443`을 제거한다.
- 상대 경로와 `.`·`..` 구간을 정리한다.
- URL fragment(`#section`)는 서버 요청에 전달되지 않으므로 일반 문서에서는 제거한다.
- 추적용 쿼리 파라미터 제거는 사이트별 규칙으로 처리한다.
- 쿼리 파라미터의 순서를 무조건 바꾸면 의미가 달라지는 사이트도 있으므로 보편 규칙으로 적용하지 않는다.

방문 URL 저장소 앞에 블룸필터를 두면 대부분의 신규 URL에 대한 저장소 조회를 줄일 수 있다. 다만 false positive가 발생하면 실제로 방문하지 않은 URL을 이미 방문했다고 판단할 수 있으므로, 수집 누락을 허용할 수 있는지에 따라 정확한 키-값 저장소와 함께 사용한다.

### 콘텐츠 중복

URL이 달라도 내용이 같은 미러 페이지나 파라미터 변형이 존재한다. 내려받은 콘텐츠를 정규화한 뒤 해시를 계산하여 같은 본문을 반복 저장하지 않는다.

- 완전히 같은 문서: 암호학적 해시로 판별
- 광고·시간표시처럼 일부만 다른 문서: SimHash나 MinHash 같은 유사도 기반 지문 사용
- 원본 응답과 정제된 본문은 목적에 따라 별도 보관

## robots.txt란?

`robots.txt`는 사이트 운영자가 자동화된 크롤러에 어떤 경로를 가져가도 되는지 알리는 **Robots Exclusion Protocol** 파일이다. `https://example.com/robots.txt`처럼 서비스의 최상위 `/robots.txt`에 놓이며, 규칙의 범위는 같은 스킴·호스트·포트의 서비스다.

```text
User-agent: StudyCrawler
Disallow: /private/
Allow: /private/help/

User-agent: *
Disallow: /admin/
```

- `User-agent`: 규칙을 적용할 크롤러를 지정한다. `*`는 별도 규칙이 없는 모든 크롤러를 뜻한다.
- `Disallow`: 가져오지 말아야 할 경로를 지정한다.
- `Allow`: 더 넓은 차단 경로 안에서 예외적으로 허용할 경로를 지정한다.
- 여러 규칙이 맞으면 경로가 가장 길고 구체적인 규칙을 적용한다. 길이가 같은 `Allow`와 `Disallow`가 충돌하면 `Allow`를 우선한다.
- `Crawl-delay`는 일부 크롤러가 지원하는 확장 지시어일 뿐 RFC 9309 표준 규칙은 아니다. 자체 크롤러는 별도의 호스트별 속도 제한을 가져야 한다.

### 가져오기와 캐시 정책

| robots.txt 결과 | 크롤러 처리 |
| --- | --- |
| `2xx` | 파싱 가능한 규칙을 준수 |
| `3xx` | 최소 5회까지 리디렉션을 따라가고 최초 서비스에 규칙 적용 |
| `4xx` | RFC상 robots.txt가 없는 것으로 보고 접근 가능 |
| `5xx` 또는 네트워크 오류 | 일시적으로 전체 경로 차단으로 간주 |

매 URL마다 `robots.txt`를 다시 받지 않고 서비스 단위로 캐시한다. RFC 9309는 접근할 수 없는 경우를 제외하면 캐시된 사본을 24시간 넘게 사용하지 않도록 권고한다. 운영 환경에서는 `4xx`를 허용으로 처리할지 더 보수적으로 막을지 정책을 명시하고, 오래된 캐시와 서버 장애가 겹친 경우의 동작도 정해야 한다.

### robots.txt가 보안 장치가 아닌 이유

`robots.txt`는 협조적인 크롤러에 대한 요청이지 인증이나 접근 제어가 아니다. 파일 자체가 공개되어 있어 차단 경로도 노출된다. 민감한 페이지는 로그인, 권한 검사, 네트워크 정책으로 보호해야 한다.

또한 다음 개념을 구분해야 한다.

- `robots.txt`: URL을 **가져오는 행위**를 제어
- `<meta name="robots" content="noindex">` 또는 `X-Robots-Tag`: 가져온 문서를 검색 색인에 넣을지 제어
- 이용약관·저작권·개인정보 정책: 수집과 저장, 재사용이 허용되는지 판단하는 별도 기준

`robots.txt`로 페이지를 막으면 크롤러는 그 페이지 안의 `noindex`도 읽을 수 없다. 따라서 “접근 차단”과 “색인 제외”를 같은 기능으로 보면 안 된다.

## SPA는 어떻게 크롤링할까?

서버 측 렌더링 페이지는 HTTP 응답의 HTML에 본문과 링크가 들어 있다. 반면 클라이언트 측 렌더링 SPA는 첫 응답에 앱 셸과 JavaScript만 있고, 브라우저가 스크립트를 실행하고 API를 호출한 뒤에 실제 DOM이 만들어질 수 있다. 이 경우 HTML만 파싱하면 빈 `<div id="root">`만 수집하게 된다.

### 먼저 구분해야 할 두 상황

1. **내가 운영하는 SPA를 검색 엔진이 잘 수집하게 만들기**
   - 서버 측 렌더링(SSR), 정적 생성(SSG), 프리렌더링 후 hydration을 우선 고려한다.
   - 사용자가 보는 내용과 크롤러가 보는 내용이 같고, 각 화면에 고유 URL과 올바른 HTTP 상태 코드가 있어야 한다.
   - 봇에만 정적 HTML을 제공하는 dynamic rendering은 운영 복잡성과 자원 비용 때문에 장기 해결책으로 권장되지 않는다.

2. **외부 SPA를 우리 크롤러가 수집하기**
   - 대상 서버의 렌더링 방식을 바꿀 수 없으므로 Playwright 같은 헤드리스 브라우저로 JavaScript를 실행한다.
   - 브라우저 렌더링은 일반 HTTP 다운로드보다 CPU·메모리·시간 비용이 훨씬 크므로 모든 페이지에 적용하지 않는다.

### 2단계 수집 파이프라인

#### 1단계: 저비용 정적 수집

- 일반 HTTP 클라이언트로 HTML을 받는다.
- 응답 HTML에서 본문과 `href` 링크를 먼저 추출한다.
- 본문이 충분하면 그대로 저장하고 종료한다.
- 본문이 거의 없고 큰 JavaScript 번들, 앱 루트 요소, SPA 프레임워크 흔적만 있으면 렌더링 큐로 보낸다.

#### 2단계: 브라우저 렌더링

- 크롤링 작업마다 비영속 Browser Context를 사용하여 쿠키와 저장소를 격리한다.
- 페이지를 열고 JavaScript 및 필요한 API 요청이 끝날 때까지 기다린다.
- `networkidle` 하나에만 의존하지 않고 최대 대기 시간, 필요한 DOM 선택자, DOM 안정 시간처럼 종료 조건을 함께 둔다. 분석·광고 요청은 계속 발생할 수 있기 때문이다.
- 렌더링된 DOM에서 본문, 링크, canonical URL, 메타 태그를 다시 추출한다.
- 필요하면 허용된 범위 안에서 스크롤이나 “더 보기” 동작을 수행한다.
- 결과를 저장한 뒤 Context를 폐기한다.

### SPA에서 추가로 생기는 문제

| 문제 | 대응 |
| --- | --- |
| 무한 스크롤 | 최대 스크롤 횟수, 신규 항목 수, 실행 시간 제한 |
| 달력·필터 조합 | 클릭 깊이와 상태 수 제한, 의미 있는 URL만 큐에 추가 |
| 클라이언트 라우팅 | History API로 생성된 URL을 수집하고 정규화 |
| `#` 기반 라우팅 | 일반 fragment와 앱 라우트인지 사이트별로 구분 |
| 로그인 후 콘텐츠 | 명시적으로 허가된 계정과 범위에서만 별도 세션 사용 |
| 늦게 끝나는 API 요청 | 특정 응답 또는 DOM 조건을 기다리고 전체 시간 제한 적용 |
| 브라우저 팝업·다운로드 | 기본 차단하고 필요한 동작만 허용 |
| 렌더링 실패 | 제한 횟수 재시도 후 원본 HTML과 실패 원인 보관 |

JavaScript 파일, CSS, API 응답도 렌더링 과정에서 가져오는 리소스다. 엄격한 크롤러라면 브라우저의 네트워크 요청을 가로채 각 URL에 `robots.txt` 정책과 접근 범위를 적용해야 한다. 스크립트가 차단되면 완전한 렌더링이 불가능할 수 있으며, 이때 차단을 우회하지 않고 부분 수집 또는 실패로 기록한다.

### 렌더러의 보안과 자원 격리

외부 페이지의 JavaScript는 신뢰할 수 없는 코드다. 렌더러는 일반 다운로더와 별도 워커 풀로 분리하고 다음 제한을 둔다.

- 컨테이너 또는 샌드박스에서 실행
- 사설 IP, 클라우드 메타데이터 주소, 로컬 파일 접근 차단
- 페이지별 CPU, 메모리, 응답 크기, 실행 시간 제한
- 다운로드, 알림, 카메라, 마이크 등 불필요한 권한 차단
- 쿠키와 캐시를 작업 간 공유하지 않음

이 분리는 악성 페이지로부터 시스템을 보호할 뿐 아니라 느린 SPA가 일반 HTML 수집 처리량까지 떨어뜨리는 것도 막는다.

## 저장 구조

- **원본 콘텐츠**: HTML과 렌더링 결과는 크기가 크므로 분산 객체 저장소에 둔다.
- **메타데이터**: URL, 상태 코드, 수집 시각, 콘텐츠 해시, 다음 방문 시각, 저장 위치는 키-값 또는 문서 저장소에 둔다.
- **방문 URL**: 조건부 쓰기나 원자적 삽입을 지원하는 분산 저장소로 중복 작업을 막는다.
- **큐**: 작업이 완료되기 전에 워커가 죽으면 다시 전달되도록 lease 또는 visibility timeout을 사용한다.

페이지 저장과 큐 확인을 하나의 분산 트랜잭션으로 묶기 어렵기 때문에, 처리기는 멱등성을 가져야 한다. 같은 작업이 두 번 실행되어도 URL 키와 콘텐츠 해시를 기준으로 최종 결과가 한 번 처리한 것과 같아야 한다.

## 장애 처리와 관측 지표

- DNS 오류, 연결 시간 초과, `5xx`: 제한 횟수 내 지수 백오프로 재시도
- `404`, `410`: 장기 재방문 주기를 적용하거나 종료 상태로 기록
- `429`: `Retry-After`를 우선하고 호스트별 속도 감소
- 리디렉션 루프: 최대 횟수 이후 실패 처리
- 파서 오류: 원본 응답을 보관하여 파서를 수정한 뒤 재처리
- poison URL: 반복 실패 횟수 초과 시 격리 큐로 이동

운영 시에는 전체 QPS뿐 아니라 호스트별 QPS, 성공률, 상태 코드 분포, 큐 대기 시간, 중복 제거율, robots 차단율, 렌더링 큐 비율, 렌더링 시간과 메모리 사용량을 관찰해야 한다. 특히 렌더링 대상 비율이 갑자기 늘면 전체 처리 비용이 크게 증가한다.

## 핵심 정리

- 크롤러의 핵심은 다운로드보다 URL 프런티어와 호스트별 스케줄링이다.
- URL 중복과 콘텐츠 중복은 서로 다른 단계에서 제거해야 한다.
- `robots.txt`는 접근 허가 요청을 표현하는 공개 규약이며 보안 장치가 아니다.
- SPA는 정적 수집 후 필요한 페이지만 브라우저 렌더링하는 2단계 구조가 효율적이다.
- 외부 JavaScript 실행은 비용과 보안 위험이 크므로 별도 워커 풀과 강한 제한이 필요하다.
- 분산 큐는 중복 전달될 수 있다고 보고 전체 처리 과정을 멱등하게 설계해야 한다.
