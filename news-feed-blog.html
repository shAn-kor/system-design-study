뉴스 피드는 언제 미리 만들어야 할까?

Pull, Push, Hybrid를 같은 코드와 부하로 비교했다. 빨라진 지점보다 비용이 옮겨간 지점을 기록했다.

뉴스 피드 설계 문제를 만나면 보통 Fan-out on write와 Fan-out on read를 비교한다. 설명은 간단하지만, 어느 비용이 실제로 커지는지는 직접 구현하기 전까지 잘 보이지 않는다. 이 프로젝트에서는 두 전략과 Hybrid를 하나의 Go 코드베이스에 넣고 동일한 fixture와 부하로 측정했다.

질문은 하나였다. 같은 역시간순 피드를 제공할 때 게시물 작성 비용, 피드 조회 비용, 저장 공간, 노출 지연을 어디에 배치할 것인가?

빠른 피드는 비용이 사라진 결과가 아니다. 사용자가 읽기 전에 누군가 먼저 계산한 결과다.

PostgreSQL의 posts를 원본으로 두고, Redis의 사용자별 피드는 삭제해도 다시 만들 수 있는 projection으로 정의했다. 이 구분이 있어야 Push의 저장 증폭을 받아들이면서도 장애 복구 방식을 설명할 수 있다.

Pull은 단순하지만, 읽을 때 모든 후보를 만난다

Pull 전략은 피드 요청이 들어올 때 현재 팔로우 관계와 게시물을 조인하고 최신 20개를 정렬한다. 작성 경로는 가볍고 결과는 항상 원본에 가깝다. 문제는 사용자가 보는 항목 수가 아니라 후보 게시물 수에 따라 조회 비용이 커진다는 점이다.

120.06ms following 5,000명일 때 feed p95
100,000 반환 20개를 위해 만난 후보 post
215,846 EXPLAIN에서 관찰한 shared buffer hit
100명 13.80ms
1,000명 38.88ms
5,000명 120.06ms

10 req/s, 5초, 조건별 3회 측정의 중앙값이다. 짧은 로컬 실험이므로 운영 SLO가 아니라 비용 변화의 방향을 확인하는 자료다.

following이 100명에서 5,000명으로 50배 늘자 HTTP p95는 13.80ms에서 120.06ms로 증가했다. SQL은 최신 20개를 반환하기 전에 최대 100,000개 게시물을 훑고 정렬했다. 다음 전략에서는 이 계산을 읽기 시점에서 작성 시점으로 옮겼다.

Push는 읽기 비용을 작성 이후로 옮긴다

게시물과 outbox event를 같은 PostgreSQL 트랜잭션에 저장한다. Relay가 event를 Redpanda에 전달하면 worker가 follower별 Redis Sorted Set에 post_id를 기록한다. 피드 조회는 미리 만들어진 ID 20개를 읽고 PostgreSQL에서 본문을 한 번에 가져온다.

->

->
Worker
Redis projection

작성 응답과 피드 노출 완료를 분리한다. event 전달과 fan-out 실패는 재시도 가능한 상태로 남는다.

정렬은 모든 score를 0으로 두고 member 문자열 (created_at, post_id)의 사전식 순서를 사용했다. timestamp가 같아도 post ID가 순서를 결정한다. 커서 역시 exclusive lexicographical bound가 되어 페이지 사이의 중복과 누락을 막는다.

동일한 following 100명 fixture에서 Push의 feed p95 중앙값은 7.16ms였다. Pull의 14.87ms보다 빨랐지만, 그 차이는 무료가 아니었다. Redis 쓰기와 저장 공간, queue lag, 재처리 책임이 새로 생겼다.

팔로워가 많아지면 작성은 빨라도 시스템은 바쁘다

비동기 처리 덕분에 HTTP 작성 응답은 follower 수와 거의 무관했다. 그러나 post 하나가 만드는 Redis command와 key 수는 follower 수에 비례했다.

100,000 post 하나가 만든 Redis feed key
756ms end-to-end fan-out 완료 시간
12.24MB 현재 로컬 Redis 메모리 관찰값

100,000 follower 계정의 작성 응답은 4.77ms였지만 fan-out 완료에는 756ms가 걸렸고, post 하나가 약 12.24MB를 사용했다. API latency만 보면 문제가 없어 보인다. 큐 체류 시간과 Redis 저장 증폭을 함께 봐야 병목이 드러난다.

Hybrid는 대형 계정의 쓰기를 읽기로 되돌린다

학습 환경에서는 follower 100,000명을 임계값으로 두었다. 그보다 작은 계정은 Push하고, 대형 계정은 fan-out을 건너뛴 뒤 피드 조회 때 PostgreSQL에서 읽는다. 두 결과는 (created_at, post_id) 역순으로 merge하고 중복을 제거한다.

Hybrid 일반 계정은 Push, 대형 계정은 Pull
절약
대형 계정 post의 Redis write 100,000회 제거
추가 비용
대형 계정을 팔로우한 모든 read에서 후보 조회와 merge
초기 임계값
100,000 followers, 학습 환경의 관찰 경계
운영 판단
작성 빈도, active follower 비율, 허용 lag를 함께 고려
Hybrid의 첫 번째 측정은 p95 31.68ms였다. celebrity 여부를 post row마다 세는 상관 서브쿼리가 원인이었다. celebrity author 집합을 먼저 구하도록 바꾼 뒤 p95 중앙값은 7.85ms가 됐다.

Hybrid라는 이름 자체가 읽기를 빠르게 만들지는 않는다. Pull branch의 후보 집합을 작성자 단계에서 줄이지 않으면, celebrity가 한 명도 없는 fixture에서도 모든 post에 follower count 비용을 낸다. 전략보다 쿼리 모양이 먼저 병목이 될 수 있다.

Projection은 언제든 다시 만들 수 있어야 한다

Push와 Hybrid는 정상 경로만 빠르게 만드는 것으로 끝나지 않는다. worker가 죽거나 Redis가 비워졌을 때 원본을 잃지 않고 다시 수렴해야 한다.

Worker가 5,122개를 쓰고 종료됐다

Kafka offset은 Redis projection이 모두 성공한 뒤에만 commit한다. 처리 중 worker를 종료하자 Redis에는 일부 write가 남고 consumer lag은 1이었다. 같은 group ID로 재시작하니 event를 처음부터 다시 처리해 100,000개 key를 완성했고 lag은 0이 됐다.

중복 재처리는 같은 결과로 수렴했다

같은 Sorted Set member에 대한 ZADD는 항목을 늘리지 않는다. 재시작 과정에서 이미 쓴 follower를 다시 처리해도 feed item은 하나만 남았다.

Redis 전체 유실도 원본 데이터 손실은 아니었다

Redis key를 모두 비운 뒤 PostgreSQL의 post를 기존 fan-out 처리기로 replay했다. Push 기준으로 post 1개, fan-out write 100,000회, Redis key 100,000개가 다시 만들어졌다. 현재 절차는 쓰기를 멈추는 오프라인 복구다.

오래된 projection은 읽기 시점에 막았다

언팔로우해도 Redis에는 과거 post ID가 남을 수 있다. 피드 hydrate 단계에서 현재 follow 관계를 다시 확인하고, stale 참조 때문에 페이지가 비면 다음 lex 구간을 이어 읽어 유효 항목으로 채웠다.

최종 선택은 하나의 전략이 아니라 경계다

following 100명, post 2,000개 조건에서 feed p95 중앙값은 Pull 14.87ms, Push 7.16ms, Hybrid 7.85ms였다. 이 숫자만 보면 Push가 답처럼 보인다. 하지만 대형 계정 post 하나가 100,000 write와 약 12.24MB를 만들었다는 관찰을 함께 놓으면 결론이 달라진다.

Pull 14.87ms
Push 7.16ms
Hybrid 7.85ms

일반 계정은 Push로 읽기 비용을 낮추고, 대형 계정은 Pull로 쓰기 증폭을 피한다. 이 경계는 follower 수 하나로 고정할 수 없다. 작성 빈도, 활성 follower 비율, 허용 노출 지연, Redis 단가가 달라지면 임계값도 다시 계산해야 한다.

이번 실험이 답한 것은 “어떤 전략이 가장 빠른가”가 아니다. 더 중요한 답은 “어떤 사용자 분포에서 어느 비용을 지불할 것인가”였다.
